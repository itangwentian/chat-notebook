# Design

## Context

配对身份目前完全依赖 `LanIdentity` 的证书指纹，而该证书密钥存放在 AndroidKeyStore，卸载即删除；`LanTrust` 又用配对时的本机指纹判断条目是否属于当前安装。结果是卸载重装后本机指纹变化，同步入口会删除全部已配对设备；对端仍保存旧指纹，只有重新配对才能恢复，而重新配对又会因指纹不同新增同名条目。设备名此前只取 `Build.MODEL`，同型号设备无法区分。参见 proposal.md。

## Goals / Non-Goals

**Goals:**

- 用跨卸载重装稳定的设备码识别同一台物理设备，并让再次配对复用原条目。
- 用用户可读名称展示对端，并在同名时提供可区分的后缀。
- 本机密钥变化时保留并重绑定信任，而不是清空；重配对后自动恢复同步。
- 兼容已保存的旧信任记录，不要求仅升级就重新配对。

**Non-Goals:**

- 不改变同步数据格式、附件传输、冲突合并规则和 TLS 认证强度。
- 不引入账号、云端设备注册或跨设备密钥托管。
- 不把设备码当作认证凭据，也不替代一次性配对令牌。
- 不处理用户手动修改系统设备名之外的别名编辑功能。

## Decisions

### 设备码：ANDROID_ID 派生

设备码 = `SHA-256("chat-notebook-device:" + Settings.Secure.ANDROID_ID)`，输出 64 位十六进制，与现有指纹格式一致，便于复用校验。Android 8+ 中 `ANDROID_ID` 与应用签名、用户和设备绑定，卸载重装不变。

- 备选：AndroidKeyStore 生成并保存随机标识 —— 卸载同样删除，无法解决本问题。
- 备选：SharedPreferences 保存 UUID —— 卸载即丢失，且备份恢复到新机时会错误复用。
- 备选：读取序列号或 IMEI —— 需要受限权限，且新系统不可用。
- `ANDROID_ID` 为空时（极少见）退化为持久化在局域网偏好中的随机值，并在文档与代码注释中标注其不跨重装。
- 设备码只在配对信令中用于“是否为同一台设备”的匹配，连接仍由 TLS 证书指纹与一次性令牌认证。

### 设备名：系统设备名优先

优先读取 `Settings.Global.DEVICE_NAME`（Android 7.1+ 公开常量）；为空时使用“厂商 + 型号”并做首字母大写、去重与长度限制。备选蓝牙名称需要 `BLUETOOTH_CONNECT` 权限，`ro.product.marketname` 属于隐藏属性，均不采用。

### 信任记录扩展与迁移

`LanTrust` 增加对端 `deviceCode` 与本机 `localDeviceCode`，均带空串默认值，保证旧 JSON 可解码；保留 `localFingerprint` 字段用于旧记录判定。读取时执行一次归一化：

1. 条目的本机设备码非空且与当前设备码不同 → 视为其他设备的备份数据，清理。
2. 条目属于本机（设备码相同，或旧记录本机指纹匹配）→ 保留；若本机指纹已变化，则更新为当前指纹（重绑定）。
3. 旧记录（无设备码）→ 保留并补写当前设备码与指纹，实现无损迁移。

配对成功后按以下顺序替换而非追加：对端设备码相同 → 替换；证书指纹相同 → 替换；新对端有设备码且存在唯一同名、或名称等于对端型号的旧条目 → 替换该旧条目。设备名从型号升级为可读名称后，名称可能变化，因此旧条目同时用旧版本上报的型号匹配。相比“按名称全局去重”，限定“唯一候选”可避免两台同型号旧设备被错误合并。

### 配对协议升级

配对请求与确认消息新增设备码，并将配对协议版本从 2 升到 3；二维码字段保持原样，避免旧版本因未知字段直接报“内容无效”。双方在解码与握手阶段校验版本：不一致时明确提示“配对版本不兼容，请更新两台设备”，不写入任何信任。已保存信任的 TLS 指纹未变，升级本身无需重新配对。

### 界面区分

列表仍以设备名为主；当已配对设备中出现重名时，为每条同名条目追加 `· 设备码后四位`。移除确认、错误提示与状态消息复用同一标签计算，避免用户移除错对象。名称唯一时不追加，保持简洁。

## Risks / Trade-offs

- [ANDROID_ID 在恢复出厂设置、更换签名或部分深度定制系统上会变化] → 视为新设备，依靠重新配对与同名旧条目迁移恢复；不把它作为安全凭据，不影响数据安全。
- [旧版本同名且同型号的两台设备无法区分] → 仅当同名旧条目恰好一条时合并，否则保留两条，让用户手动移除错误项，避免误合并。
- [本机重绑定后、重配对前，连接会被对端拒绝] → 界面明确提示重新扫码，配对成功即恢复；不自动删除条目以免用户丢失配对信息。
- [配对协议升级导致新旧版本不能配对] → 提示更新两台设备；已配对设备不受影响。
- [设备码后四位可能重复] → 仅在同名条目上作为区分提示，真正身份判断始终使用完整设备码与指纹。

## Migration Plan

1. 发布后首次启动：旧信任记录按空默认值解码，并在首次同步或配对时归一化，补写设备码。
2. 两台设备都升级后重新配对：新信令携带设备码，旧条目被替换或复用。
3. 回滚：恢复旧版本后设备码字段被忽略，证书指纹仍有效，已配对关系继续可用；协议版本回退会导致重新配对需要两台设备同为旧版本。
