# Design

## Context

动机与行为范围见 proposal.md 和 `specs/attachment-lifecycle/spec.md`。当前 `PersistentChatRepository.deleteSession` 调用 `ChatSessionService.delete`，后者通过 `RecordRepository.update` 持久化会话删除；按会话拆分的仓库会在成功保存后移除该会话文件。消息附件元数据以相对路径保存，转发消息会复制附件元数据，因此不同对话可能共用同一文件。`AttachmentStore.delete` 在记录目录中删除附件文件，现有单消息软删除不会删除附件。

## Goals / Non-Goals

**Goals:**
- 只清理被删除对话引用且其他未删除对话均未引用的附件路径。
- 先持久化对话删除，再清理文件；确保记录写入失败时不会丢失仍被对话引用的附件。
- 序列化会影响附件引用的仓库操作，避免在引用统计与删除文件之间新增转发引用。
- 让文件系统清理失败明确到达现有 UI 操作提示。

**Non-Goals:**
- 不更改单条消息软删除、合并或草稿移除的附件语义。
- 不扫描并清理历史孤立文件，也不更改快照格式、Room schema 或 SAF 目录结构。
- 不提供自动重试队列或附件清理管理界面。

## Decisions

### 删除后比较引用路径集合

删除前收集目标对话所有消息中的附件 `relativePath`，去重后作为候选集合。持久化删除成功后，从新的记录状态中收集所有未删除对话的消息附件路径；消息自身的软删除标记不排除引用，因为这些消息仍保存在对话快照中。候选集合减去剩余引用集合即为待删除文件。

以路径而非附件 ID 作为共享判断依据，因为文件存储定位使用相对路径，转发会保留相同路径。其他未删除对话即使只在其软删除消息中保留该路径，也继续持有引用。

替代方案：按被删对话逐条删除附件，会误删转发到其他对话的文件；按附件 ID 计数无法表达不同记录对同一文件路径的引用。

### 在持久化提交后执行文件清理

先运行现有对话删除更新，只有其会话文件成功写入并从仓库当前状态移除后，才调用附件存储删除待清理路径。将删除会话、发送和转发这些可能改变附件引用集合的操作纳入同一仓库互斥区间，使引用计算至文件删除完成期间不会产生新的附件引用。

替代方案：先删文件再保存对话会让快照写入失败时，仍存在的对话变成附件不可用；把二进制附件纳入记录快照则改变现有存储格式且不必要。

### 显式呈现部分清理失败

逐个尝试删除待清理文件；收集删除失败并在所有候选都已尝试后返回明确异常。对话删除保持已持久化，不回滚快照；错误传至 `ChatViewModel` 现有的 `runAction` 提示路径，并使用可理解的中文清理失败信息。成功删除前已被其他对话引用的路径不进入删除尝试。

替代方案：吞掉异常会把附件残留伪装成完整成功；回滚对话删除也无法安全恢复已经成功删除的部分附件。目录权限丢失等错误因此明确报告为“对话已删除、附件清理未完成”。

## Risks / Trade-offs

- [记录目录权限在对话删除后失效] → 对话仍按已提交状态删除，清理失败明确提示；不静默吞错或尝试恢复消息记录。
- [删除多个附件时只有部分文件删除成功] → 尝试所有不再引用的路径并汇总失败路径，已成功删除的文件无需回滚。
- [消息转发增加附件引用] → 在统一互斥区间内串行化转发、发送与对话删除，直到附件清理结束。
- [历史上已存在无引用附件] → 本次只清理被删除对话贡献的引用，不做目录全量扫描，以避免删除无法归属或未被当前索引发现的文件。

## Migration Plan

1. 增加可测试的引用集合差分逻辑及数据层测试，不变更既有记录格式。
2. 在仓库删除对话流程中加入提交后清理与引用修改操作互斥，并为失败提供明确错误。
3. 更新删除对话的 ViewModel/UI 提示测试；运行相关单元测试、`testDebugUnitTest`、`lintDebug` 和 `assembleDebug`。

无需数据迁移。若实现或验证失败，回退本变更的仓库清理逻辑即可，既有会话快照及附件文件格式保持兼容。
