# Design

## Context

默认对话只在 `ChatRepository.open()` 判定“记录目录没有任何文件”时创建。该判断把无关文件、空的 `attachments` 子目录都当成“已有数据”，导致用户选择下载/文档等常见目录时看不到默认对话。

记录目录中本应用的数据文件包括：会话文件（`session-*.json`）、设置文件（`settings-*.json`）、同步日志和旧版笔记文件。判断依据应以这些文件是否存在为准。

## Goals / Non-Goals

**Goals:**

- 目录中没有本应用记录数据时创建默认对话并选中“草稿”，即使目录里有无关文件或空子目录。
- 目录中已有本应用记录数据时一律不创建，包括删除全部对话后重开、重装后重新选择原目录。
- 判断只读取目录文件名，不读取或解析文件内容，避免额外 IO 与格式耦合。

**Non-Goals:**

- 不修改默认对话的名称与分组行为。
- 不清理目录中的无关文件或空目录。
- 不改变旧版笔记迁移、记录恢复与同步逻辑。

## Decisions

### 用“是否存在本应用记录文件”替代“目录是否为空”

`RecordRepository.restore()` 本来就会列出目录根文件并区分会话文件、设置文件、旧版笔记与同步日志。在恢复时记录 `sessions.isNotEmpty() || settings.isNotEmpty() || legacy.isNotEmpty() || restoredSync != null`，通过只读属性暴露给 `ChatRepository.open()`。

选择这个方案的原因：

- 与用户对“已有我们的数据”的理解一致，不受无关文件影响。
- 删除对话后设置文件仍存在，避免重新打开时自动重建默认对话。
- 复用恢复流程已有的文件名分类，不新增目录扫描。

考虑过的替代方案：把“目录为空”放宽为“忽略无关扩展名”。该方案仍需维护文件白名单，且空 `attachments` 目录无法区分是遗留还是本应用创建，因此不采用。

### 判断必须发生在 `ensureWritable()` 之前

`ensureWritable()` 在空目录会写入一个空设置文件。如果在其之后再判断，空目录会被误判为“已有数据”。因此 `restore()` 在写入任何文件前完成标记，`open()` 只在初始化后读取该标记并决定是否创建默认对话。

### 默认对话创建的防御性判断

`ChatSessionService.seedDefaultConversations()` 保留“已有对话则返回 null”的防御检查，改为检查内存中是否存在任何会话（含已删除），与“目录已有记录数据就不创建”保持一致。外部条件（见上）仍是主要判定。

## Risks / Trade-offs

- [目录只有 `attachments` 残留、没有设置或会话文件] → 视为没有记录数据并创建默认对话；这是期望行为，用户需要可用的默认入口。
- [恢复过程中发现损坏文件] → 维持现有行为：恢复失败并提示，不会创建默认对话，避免覆盖用户数据。
- [同步日志存在但会话为空] → 视为已有本应用数据，不创建默认对话，避免在已启用同步的目录里产生重复对话。

## Migration Plan

无需数据迁移。旧目录中的设置文件、会话文件或同步日志会自然让标记为真，保持“不重建默认对话”的既有行为；全新的空目录或只含无关文件的目录会在下次打开时补齐默认对话。
